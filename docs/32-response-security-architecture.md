# Response Security Architecture

AutoSOC strictly enforces human oversight for all containment and response actions to prevent autonomous disruption of legitimate business services.

## Operational Modes

### 1. Recommendation Mode (Default)
The Rule Engine or Agentic AI identifies a potential containment action (e.g., "Block IP 10.0.0.5"). This recommendation is inserted into the `response_approvals` table with a status of `PENDING`. No external infrastructure is touched.

### 2. Dry-Run Mode (Simulation)
An Analyst reviews a `PENDING` action and clicks "Simulate". The Response Worker executes the playbook against a mock target (or runs a read-only impact analysis script) and returns the expected result (e.g., "This will block 5 active sessions"). The action remains `PENDING`.

### 3. Analyst-Approved Execution
The Analyst clicks "Approve". 
1. The API verifies the Analyst's OIDC token and RBAC permissions.
2. The API updates the database record to `APPROVED`, logging the `approver_id` and timestamp.
3. The API publishes an event to the `security.response.tasks` Redpanda topic.
4. The Response Worker consumes the event, verifies the DB status is indeed `APPROVED`, and executes the action.

### 4. Restricted Automatic Execution (Future Capability - Out of Scope for MVP)
In a future phase, highly deterministic rules (e.g., known malware hash) could bypass human approval, but this requires an explicit override flag set by the Administrator.

## Safeguards

- **Playbook Allowlist**: The Response Worker can only execute scripts/API calls defined in a strict, hardcoded repository of playbooks. It cannot execute arbitrary commands generated by the LLM.
- **Target Validation**: The target of the action (e.g., an IP address) is validated against a "Do Not Touch" list (e.g., Domain Controllers, internal gateways) before execution.
- **Maximum Scope**: Actions are scoped to single entities (one IP, one user). Mass actions require manual Administrator intervention.
- **Separation of Duties**: The Agent Worker (which proposes the action) and the Response Worker (which executes it) are entirely separate processes with different database permissions.
- **Idempotency**: Playbooks are designed to be idempotent (e.g., "Ensure IP is blocked" rather than "Add block rule").
- **Rollback**: Every Playbook must have a corresponding rollback script (e.g., "Unblock IP"). The Analyst can trigger this via the UI, which follows the same audit trail.
- **Execution Timeout**: Playbook executions timeout after 30 seconds to prevent hanging processes.
- **Emergency Disable Switch**: A global configuration flag (`ALLOW_RESPONSES=false`) can be set by the Administrator to instantly kill the Response Worker's ability to consume tasks.
